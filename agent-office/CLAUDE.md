## โปรเจกต์นี้คืออะไร

"บริษัทเปล่า" ของ AI agent ที่แสดงเป็นออฟฟิศพิกเซล 8-bit ผู้ใช้สั่งว่าอยากผลิตอะไร บริษัทผลิตให้ตามลำดับชั้น

ลำดับการทำงาน (ออกแบบไว้ 2026-10-02):

1. ผู้ใช้บอกเจ้าของบริษัท (agent ใหญ่สุด) ว่าต้องการผลิตอะไร
2. เจ้าของเก็บ requirement จนตรงใจผู้ใช้ → **ผู้ใช้อนุมัติ brief ก่อนเริ่ม**
3. เจ้าของเลือกเฉพาะแผนกที่งานนี้ต้องใช้ แล้วประชุมกับหัวหน้าแผนก
4. หัวหน้าแตกงานให้ลูกน้อง
5. ลูกน้องทำงานตามตำแหน่ง
6. ส่งงานคืนหัวหน้า → ผู้ตรวจเทียบกับ brief (ตีกลับได้ไม่เกิน 1–2 รอบ)
7. ผู้ใช้ตรวจและรับงาน

ตัวละครผู้ส่งเอกสารเป็นแอนิเมชันล้วน ไม่เรียกโมเดล

## Requirements ขั้น 1 (ตกลงกับผู้ใช้ 2026-10-02)

- **ตำแหน่ง 10 ตัว**: เจ้าของ 1, เลขาเจ้าของ 1 (จด brief / สรุปผลส่งผู้ใช้), 2 แผนก (**วิจัย** และ **ผลิตงาน**) แผนกละหัวหน้า 1 + ลูกน้อง 2, ผู้ตรวจ 1, ผู้ส่งเอกสาร 1
- **ผู้ส่งเอกสาร**: เป็นตัวจัดคิวงานจริง (โค้ดธรรมดา ไม่ใช่ AI) ถือหน้าที่ส่งต่องานระหว่างตำแหน่ง แอนิเมชันสะท้อนการส่งต่อนั้น **ใช้เฉพาะเอกสารที่ข้ามห้อง** (2026-10-03 ผู้ใช้สั่ง) ถ้าอยู่ห้องเดียวกัน (`ROOM_OF`/`sameRoom` ใน `core/world.ts`) ผู้ส่งถือเอกสารเดินไปยื่นที่โต๊ะผู้รับแล้วเดินกลับ (เหตุการณ์ `doc.handed` ไม่ผ่านคิว) ส่งซ้อนกันได้ทีละคนต่อ "เลน" ของคนนั้น
- **ภาพ**: Claude วาดสไปรต์พิกเซลเองด้วยโค้ด (ยังไม่ใช้ชุดสไปรต์ภายนอก) มุมกล้องเฉียง 3/4 แบบ Game Dev Story ตัวละครเดินได้ 4 ทิศ
- **หน้าจอ**: ภาพออฟฟิศ + แถบสถานะ (งานปัจจุบัน/ขั้นตอน) + คลิกตัวละครเพื่อดูบทสนทนา/กำลังทำอะไร
- **สั่งงาน**: กล่องแชทแบบหน้าจอสนทนา RPG คุยกับเจ้าของ (เจ้าของถามกลับหลายรอบเพื่อเก็บ requirement)
- **เดโมจำลอง**: สคริปต์ 1 งานตัวอย่างที่เล่นครบ 7 ขั้นและครบทุกเหตุการณ์ + ปุ่มทดลองเหตุการณ์พิเศษ (QA ตีกลับ, error, รอคิว ฯลฯ) ตัวจำลองต้องส่งเหตุการณ์รูปแบบเดียวกับของจริง
- **เทคนิค**: Canvas 2D ล้วน ไม่เพิ่มไลบรารีเกมจนกว่าจะจำเป็น (ผู้ใช้ยืนยัน) ข้อความใน UI/เกมรองรับ **2 ภาษา EN/TH** (ผู้ใช้สั่งเพิ่ม 2026-10-03 แทนกฎเดิมที่ให้เป็นอังกฤษล้วน) สลับได้ในเมนู ดูหัวข้อ "ภาษา (i18n)" ด้านล่าง ส่วนเอกสารโปรเจกต์ยังเป็นไทยได้

## สถานะ / ขั้นการพัฒนา

- **ขั้น 1 (เสร็จรอบแรก 2026-10-02)**: UI ออฟฟิศ + ลำดับเหตุการณ์ **จำลอง** ยังไม่ต่อ AI ไม่กิน token — ทำแล้ว: ห้อง 10 ตำแหน่ง, เดิน/นั่ง/ท่าทาง, แชท RPG, inspector, คิวคูเรียร์, ปุ่มทดลอง (QA reject / agent error / courier jam), เทสต์ 12 ข้อ รอบสอง 2026-10-03: ตึกหลายห้องกั้นด้วยฉากครึ่งความสูง ใช้งานจริง (กาแฟ/ห้องน้ำ/เก็บเอกสาร/ห้องเซิร์ฟเวอร์), ตึกเต็มหน้าต่าง, เทสต์ 61 ข้อ (รวมหน้าเว็บด้วย jsdom) ที่ยังไม่ทำ: เสียง, ซูม/แพนบนมือถือ, ประตูเปิดปิดตามคนผ่าน
- **ขั้น 2 (กำลังทำ — รายละเอียดทั้งหมดอยู่ใน `STAGE2.md`)**: ต่อ agent จริงด้วย Gemini (key ของผู้ใช้เอง ชั้นฟรี ไม่ผูกบัตร) ทำแล้ว: ช่องใส่ key, `ModelClient` + ตัวคุมอัตรา, เจ้าของ+เลขาเก็บ requirement และเขียน brief จริง, ตัวช่วยค้นเว็บในเครื่อง (`helper/`, พอร์ต 8071) + function calling, ห้องเซิร์ฟเวอร์สะท้อนการเรียกจริง, ย้อนดูงาน (replay), **แผนกวิจัยจริง** (Dr. Iris แตกงาน → Leo/Mina ค้น+อ่านเว็บ → รวมเป็นรายงานพร้อมแหล่งอ้างอิงและตรา "ตรวจ/ยังไม่ตรวจกับแหล่งจริง" ที่โค้ดเป็นคนใส่ ไม่ใช่โมเดล), แนบไฟล์ข้อความเข้า + ดาวน์โหลดผลออก (md/txt/html/csv) **เจ้าของเลือกแผนกตามงาน** (วิจัยล้วน / ผลิตล้วน / ทั้งคู่), **แผนกผลิตจริง** (Hana แตกงาน → Kai/Zoe เขียนจากบรีฟ+รายงานวิจัย → Hana รวมเป็นผลงาน), **ผู้ตรวจจริง** (Quinn เทียบกับบรีฟและหลักฐาน ตีกลับได้ไม่เกิน 2 รอบ แล้วส่งมอบพร้อมระบุข้อที่ยังแก้ไม่ครบ ไม่ซ่อน; ลิงก์ที่ไม่มีใครเปิดอ่านจริงถูกตีกลับโดยโค้ดไม่ว่าผู้ตรวจจะว่ายังไง), ตอนส่งมอบแสดงผลงานจริงในแชท และขอแก้ได้จริง (แก้ + ตรวจซ้ำ) **โควตา AI แสดงเป็นชีวิตในออฟฟิศ** (เครื่องพิมพ์ล็อบบี้ = กองหน้าที่พิมพ์ไปวันนี้/กระดาษหมด, Zip เติมกระดาษตอนโควตารีเซ็ตเที่ยงคืนเวลาแปซิฟิก, การ์ดตัวละครบอกหน้าที่พิมพ์, คนที่ทำงานหนักจะหาว; ยอดนับเฉพาะที่แอปนี้เรียก เพราะ Google ไม่บอกยอดคงเหลือ) ที่ยังไม่ทำ: PDF/docx, จอพิมพ์สด, ผู้ใช้ลองทั้งสายกับ Gemini จริงแล้ว (2026-10-06) รายงานว่าใช้งานได้ดีมาก แต่ **ยังไม่ได้วัดตัวเลข** (เวลา/จำนวนคำขอ/โควตาต่องาน) จึงยังไม่ปรับค่าตัวคุมอัตรา
- **ขั้น 3**: ลองงานจริง 1 ชิ้น วัดคุณภาพและเวลา

ยังไม่ตัดสินใจ: รูปแบบการแจกจ่าย (ฝังโมเดลในโปรแกรม / ให้ผู้ใช้ใส่ API key เอง / โหมดเดโม NPC ล้วน) — ออกแบบให้ไม่ผูกกับแบบใดแบบหนึ่ง

## สถาปัตยกรรม (หลักการ)

แยก 3 ชั้น คุยกันผ่าน "เหตุการณ์กลาง" (JSON) เท่านั้น:

```
[ UI 8-bit ] <-- เหตุการณ์ --> [ orchestrator ] <--> [ adapter ของโมเดล ]
```

- UI ไม่รู้ว่า agent ใช้โมเดลอะไร แค่วาดตามเหตุการณ์ (เช่น `agent เริ่มงาน`, `ส่งเอกสารให้หัวหน้า`, `QA ตีกลับ`, `error`)
- โมเดลของแต่ละตำแหน่งตั้งด้วย config (ตำแหน่งละบรรทัด) สลับเป็นโมเดลอื่นได้โดยไม่แก้ UI
- ขั้น 1 ใช้ตัวจำลองส่งเหตุการณ์แทน orchestrator จริง — ต้องส่งรูปแบบเหตุการณ์เดียวกับของจริง
- งานแต่ละชิ้นควรมีโฟลเดอร์ของตัวเอง (brief.md, งานของแต่ละตำแหน่ง, ผลลัพธ์) แทนการส่งข้อความยาวต่อกัน

## ภาษา (i18n) — EN/TH (ทำ 2026-10-03)

- **คำทั้งหมดอยู่ใน `src/core/strings.ts` ที่เดียว** (พจนานุกรม `en` + `th` ต้องมีครบทุก key และ placeholder ตรงกัน) โมดูล `src/core/i18n.ts`: `t(key, params)`, `msg(key, params)` (ข้อความที่ส่งต่อได้), `raw(text)` (ข้อความที่ผู้ใช้พิมพ์เอง), `setLang/onLangChange`
- **OfficeEvent พก key + params (`Msg`) ไม่พกประโยค** ฝั่ง UI แปลตอนแสดง → สลับภาษากลางแชท/ฟีดเก่าแปลตามทันที Real orchestrator ในอนาคตต้องส่ง `Msg` แบบเดียวกัน (หรือ `raw()` สำหรับข้อความดิบจากโมเดล) ชื่อ `title` ของงานเป็นข้อความผู้ใช้ จึงเป็น string
- **ปุ่มตอบคำถามเป็น `{id, label: Msg}`** และผู้ใช้ตอบด้วย `ChatReply = {choice: id} | {text}` ห้ามเทียบข้อความป้ายปุ่ม ข้อความที่พิมพ์เองจับความหมายด้วย `core/intent.ts` (อังกฤษ+ไทย: อนุมัติ/ตกลง/ยอมรับ... และคำว่า "แก้ไข" ล้วนๆ = ถามว่าจะแก้อะไร) จังหวะ pacing ของซิมไม่ผูกกับความยาวข้อความภาษาปัจจุบัน
- ชื่อตัวละคร (Rex, Sam, Dr. Iris, ...) **ไม่แปล** (ผู้ใช้ตัดสิน) แปลเฉพาะตำแหน่ง/คำอธิบาย (`role.<id>`, `blurb.<id>`) ชื่อภาษาในปุ่ม ("English" / "ไทย") คงเป็นภาษาของตัวเอง
- ข้อความใน `index.html` ใช้ `data-i18n`, `data-i18n-title`, `data-i18n-aria` (`ui/i18n-dom.ts` `applyStatic`) ห้ามเขียนคำลง HTML/TS ตรงๆ — เทสต์ `core/strings.test.ts` สแกนหาคำที่ฝังอยู่นอกพจนานุกรม
- จำภาษาใน `localStorage` (`agent-office.lang`, ห่อ try/catch) ค่าเริ่มต้น: เบราว์เซอร์ภาษาไทย → ไทย นอกนั้นอังกฤษ ปุ่มสลับอยู่ในเมนู
- **ฟอนต์ไทย**: Cascadia Mono/Consolas ไม่มีอักษรไทย โหมดไทยใช้ฟอนต์พิกเซล **Silver** (Poppy Works, CC BY 4.0, `public/fonts/Silver.ttf` 3.5 MB ไม่ได้ตัด/ดัดแปลง, ผู้ใช้อนุมัติ 2026-10-03) ผ่าน `--font-th` มีฟอนต์ระบบ (Leelawadee UI/Tahoma/Noto Sans Thai) เป็น fallback เบราว์เซอร์โหลดไฟล์เฉพาะตอนแสดงข้อความไทย ตัวอักษร Silver เล็กกว่า Cascadia ที่ font-size เท่ากัน (x-height 0.32 vs 0.52) ผู้ใช้สั่งให้ไทยดูเท่าอังกฤษ จึงใช้ **`size-adjust: 162%` ใน `@font-face` ของ Silver** (0.52/0.32) ขยายเฉพาะกลิฟของ Silver โดย **ไม่แตะ font-size/line-height/ขนาดกล่องใดๆ** เลย์เอาต์จึงเหมือนอังกฤษทุกจุด **ห้ามบังคับ font-size ในโหมดไทย** (เคยลอง 16px แล้วเล็ก ลอง 24px `!important` ทุกชิ้นแล้วกล่อง/ปุ่มสูงเพี้ยนและลำดับขนาดหาย) และ **ฟอนต์อังกฤษต้องมาก่อน Silver ใน `--font-th`** (ผู้ใช้สั่ง: ตัวเลข "1x" ชื่อ "QA" "Rex" ฯลฯ ใช้ฟอนต์อังกฤษเดิม เบราว์เซอร์ตกไปใช้ Silver เฉพาะตัวอักษรไทย) ขอบพิกเซลจึงไม่คมเท่ากริด 16px (`placeDrawer` ใน `main.ts` ดันลิ้นชักลงใต้ HUD เมื่อซ้อนกัน) เครดิตอยู่ท้ายเมนู (`credit.font`) และใน `THIRD-PARTY.md` ถ้าจะตัดไฟล์ให้เล็ก (Latin+ไทย ด้วย fonttools ใน `.venv`) ต้องจดว่าดัดแปลงด้วย เทสต์ `core/font.test.ts` เฝ้าไฟล์/การประกาศ/เครดิต
- **อ่านไทยง่ายขึ้น (ผู้ใช้ว่าไทยติดกันอ่านยาก 2026-10-03):** (1) **เว้นวรรคเฉพาะที่คนไทยเว้นจริง** คือระหว่างอนุประโยค/ก่อนคำเชื่อม (แล้ว, หรือ, เพื่อ, จะ หลังประธานยาว) **ห้ามเว้นระหว่างกริยากับกรรมหรือภายในวลี** (เช่น "กำลังไป ห้องเซิร์ฟเวอร์", "เครื่องมือของฉัน เพิ่งล่ม" ผิด — ผู้ใช้ทักว่าเว้นแปลก 2026-10-03 ผมเคยเว้นเกินแล้วต้องย้อนกลับ) และไม่ใช้ตัดคำอัตโนมัติ `Intl.Segmenter` (ตัดละเอียดเกิน "เป้า|หมาย") ข้อความใหม่ให้เว้นแบบเดียวกัน (2) CSS: `letter-spacing: 0.04em` ที่ `html[lang='th']` และ `line-height: 1.7` เฉพาะข้อความยาว (`.dlg-text .hint .blurb .convo li .feed li .queue li .kv dd`) ปุ่ม/ป้ายสั้นคงความสูงเท่าอังกฤษ และ `.dlg-text` ขยาย min/max-height ตามสัดส่วนไม่งั้นกล่องแชทจะมีแถบเลื่อน (3) ทางสำรองถ้ายังอ่านยาก: ปุ่มเลือกฟอนต์ไทย "พิกเซล/อ่านง่าย" (ฟอนต์ระบบ)
- เพิ่มข้อความใหม่: ใส่ key ทั้ง `en` และ `th` ใน `strings.ts` แล้วใช้ `t()`/`msg()` เท่านั้น

**ชั้น AI (ขั้น 2)** — `src/ai/` (ฝั่งเบราว์เซอร์) + `helper/` (Node ในเครื่อง, ไม่แตะ API key):
- `model-client.ts` อินเทอร์เฟซโมเดล + `ModelError` (UI แปลตาม `kind` ไม่แสดง message), `gemini.ts` adapter, `limiter.ts` ตัวคุมอัตราตัวเดียวทั้งบริษัท, `models.ts` โมเดลต่อตำแหน่ง (`MODEL_FOR`)
- `gemini-brain.ts` + `prompts.ts` เจ้าของ/เลขา (IntakeBrain) · `gemini-research.ts` + `research-prompts.ts` แผนกวิจัย (`core/research.ts` = อินเทอร์เฟซ `ResearchBrain`) · `brain-factory.ts` เลือก Gemini หรือสคริปต์เดโมต่องาน (`chooseBrain` / `chooseResearch`; ไม่มี key = สคริปต์เดโมเดิมทั้งหมด)
- `tool-runner.ts` + `agent-tools.ts` function calling กับ `web_search`/`news_search`/`read_page` ผ่าน `toolbox.ts` → helper; `unverifiedUrls` จับลิงก์ที่โมเดลอ้างแต่ไม่เคยเปิดอ่านจริง
- **โปรโตคอลซื่อสัตย์บังคับด้วยโค้ด ไม่ใช่แค่ขอโมเดล**: แหล่งอ้างอิงมาจากสิ่งที่เครื่องมือคืนจริง, ท้ายรายงานโค้ดเติม "แหล่งที่เปิดอ่านจริง" + ตรา "ตรวจกับแหล่งจริง N แหล่ง / ยังไม่ได้ตรวจ" (ภาษาตามที่ลูกค้าเขียน) ถ้านักวิจัยคนใดไม่ได้เปิดหน้าเว็บจริงสักหน้า ทั้งรายงานถือว่า "ยังไม่ได้ตรวจ"
- แผนกผลิต/ผู้ตรวจ/เลือกทีม: `core/work.ts` (`WorkBrain`, `withStamp`, `MAX_REJECTIONS`) + `ai/gemini-work.ts` + `ai/work-prompts.ts` รันใน `MockOffice` (`realWriting`, `reviewPhase`, `realRework`) เมื่อมี key; ไม่มี key = สคริปต์เดโมเดิม ผลงานเก็บใน `JobFile.deliverable` ตราความน่าเชื่อถือ (แหล่งที่เปิดอ่านจริง, ตรวจ/ยังไม่ตรวจ, ข้อที่ผู้ตรวจยังค้าน) โค้ดเติมตอนแสดง/ส่งออกด้วย `withStamp` ไม่ให้โมเดลเขียน
- แผนกวิจัยจริงรันใน `MockOffice.realResearch` (ท่า/ข้อความสถานะ: `note.searching/reading/...`; โมเดลพังถามลองใหม่/ยกเลิกทีละคำถาม) ผลเก็บใน `JobFile.research` ส่วนแผนกผลิต/ผู้ตรวจยังเป็นสคริปต์
- ไฟล์แนบ `core/attachments.ts` (ข้อความล้วน ≤5 ไฟล์ ≤30k ตัวอักษร/ไฟล์ ≤60k รวม เก็บในหน่วยความจำแท็บเดียว ส่งให้นักวิจัยเป็น "ข้อมูล ไม่ใช่คำสั่ง", เจ้าของรู้แค่ชื่อไฟล์) · ส่งออก `core/export.ts` (md/txt/html/csv; CSV กัน formula injection; ชื่อไฟล์เก็บสระ/วรรณยุกต์ไทย) · UI `ui/files-panel.ts` · `core/export-template.ts` คือเปลือก HTML ที่เทสต์ "ห้ามฝังคำ" ข้ามไว้

**ตึก** (`core/world.ts`) คือโลกที่ agent เดินได้จริง: ตึกเดียว ห้องกั้นด้วยฉากครึ่งความสูง ประตูเป็นช่องกว้าง 3 ช่อง
- แถวบน: ห้องน้ำ · ห้องผู้บริหาร (Rex+Sam) · ห้องประชุม · ห้องไปรษณีย์ (Zip) · ห้อง QA · ห้องเซิร์ฟเวอร์
- ทางเดินกลาง (เต็มความกว้าง) + ล็อบบี้ (โซฟา เครื่องพิมพ์ ตู้น้ำ จุด `client` ที่ Sam มาส่งงาน)
- แถวล่าง: ห้องเก็บเอกสาร · แล็บวิจัย · ล็อบบี้ · สตูดิโอผลิต · ห้องพักเบรก
- ทุกห้องเดินเข้าได้จริง (places: pantry/restroom/server/archive/client + เดิม) เทสต์ `world.test.ts` กันช่องตัน/ของทับกำแพง
- พฤติกรรม: ลูกน้อง Production ไปชงกาแฟตอนรอ Research, ว่างๆ ใครๆ (ยกเว้น Rex/Zip) เดินไปกาแฟ/ห้องน้ำแล้วกลับโต๊ะ, Sam เก็บงานที่รับแล้วเข้าห้องเอกสาร (ชั้นวางเต็มขึ้นตามจำนวนงาน), ห้องเซิร์ฟเวอร์ไฟกะพริบตามจำนวน agent ที่ทำงาน/พัง และเมื่อ agent พัง **หัวหน้าเดินไปรีสตาร์ตเซิร์ฟเวอร์ที่ห้องเซิร์ฟเวอร์จริง** แล้ว agent กลับมาทำงาน หัวหน้ากลับโต๊ะ (หัวหน้า Research เดินทางเดียวราว 9.7 วิ, Production ราว 4.8 วิ ที่ 1x)

**เลย์เอาต์จอ** (`core/layout.ts`): ตึกคงที่ 472x224 วางกลางแคนวาสที่ใหญ่เท่าหน้าต่าง สเกลเป็นจำนวนเต็มเมื่อจอพอ (คม) ผนังหลังที่สูงขึ้นบนจอสูงเป็น **ผนังเรียบ ไม่มีหน้าต่างซ้ำ ไม่มีลายตกแต่ง** (ผู้ใช้สั่ง ห้ามซ้อนแถวหน้าต่าง) ทั้งตึกสว่างเท่ากัน **ห้ามมีเงามืดที่ขอบ/สปอตไลต์กลางจอ** (ผู้ใช้สั่งเอาออก) เครื่องพิมพ์อยู่ในมุมถ่ายเอกสารชิดผนังฝั่งแล็บของล็อบบี้ (ผู้ใช้ไม่ชอบเครื่องลอยกลางห้อง) เหลือหน้าต่างเฉพาะของห้องจริง (ผู้บริหาร/QA/ห้องน้ำ) ที่เกินจอเป็น **ภายในตึกที่ต่อเนื่องออกไป** (`render/decor.ts`) เท่านั้น — ผู้ใช้สั่งชัดว่า **ห้ามมีภายนอกตึก** (ที่จอดรถ ต้นไม้ ถนน) และ **ห้ามมีพรมแถบยาว/พรมต้อนรับ/เสื่อเช็ดเท้า** พิกัดทุกอย่างเป็นพิกัดตึก ชั้นวาดใช้ `translate(ox, oy)` และเมาส์แปลงด้วย `view.toOffice()` ห้ามใส่ของที่ agent เดินถึงนอกตึก
ความกว้างของตึกถูกเลือกให้ **สเกลไม่ตกบนจอทั่วไป** (เทสต์ `layout.test.ts` เฝ้าไว้) ก่อนขยายตึกต้องรันเทสต์นี้ ส่วนความสูงควรคง 224 (ความสูงคือตัวจำกัดสเกลของจอส่วนใหญ่)
HUD เล็กลอยมุมจอ ปุ่มอื่นอยู่ในลิ้นชัก Menu เพื่อให้ภาพได้ทั้งหน้าต่าง
**กล้อง** (ui/camera-controls.ts, ตรรกะ core/camera.ts): เริ่มที่ภาพพอดีหน้าต่าง ซูมเข้าด้วยลูกกลิ้งเมาส์ / ปุ่ม + − / + - (สเกลจำนวนเต็มถัดขึ้นไป) แล้วเลื่อนดูได้ด้วย เมาส์ชิดขอบจอ (เฉพาะตอนเมาส์อยู่บนภาพ ไม่ใช่บน HUD/เมนู/แชท), WASD/ลูกศร, หรือลากเมาส์/นิ้ว **กล้องเลื่อนได้เฉพาะในตัวตึกที่ใช้งานจริง** ไม่เลื่อนไปห้องตกแต่งนอกตึก (ผู้ใช้สั่ง) พื้นหลังเป็น texture ครั้งเดียวไม่สร้างใหม่ตอนเลื่อน
**ผนัง/ประตู** (`render/rooms.ts` `drawWallCell`): ใช้ **ฉากกั้นครึ่งความสูงอย่างเดียว** และ **ไม่มีบานประตู** (ช่องประตูเป็นช่องเปิดโล่ง มีแค่ไฟสถานะที่ประตูห้องน้ำ/เซิร์ฟเวอร์) **ไม่มีไอคอนป้ายห้อง** ที่พื้นหน้าประตู (ผู้ใช้สั่งเอาออกทั้งหมด) ผู้ใช้เคยลองกระจกเต็มความสูง/ประตูบานพับแล้วเปลี่ยนใจเอาออก (2026-10-03) ถ้าจะลองใหม่ ดู commit `5b6dce7` (กระจกแบบ A เสาเฉพาะปลายผนัง + ประตูบานคู่ที่เปิดเอง) ข้อที่ผู้ใช้ไม่ชอบ: เส้นตั้งถี่เหมือนซี่กรง, ฟิล์มฝ้า/แผ่นเตะ, โลโก้แผนกยังไม่ทำ: บีบนิ้วซูม/ลากบนมือถือแนวตั้ง (ตึกจะเล็ก) **ทำพร้อมกันทีเดียว (ผู้ใช้สั่งเก็บไว้ 2026-10-03):** ที่ความกว้าง ~375px กล่องแชทของ Sam ที่อยู่ด้านบน (`.dialog.top`) ถูก HUD ที่ตกเป็น 2 แถวทับ ชื่อถูกบังและท้ายข้อความถูกตัด (เกิดทั้ง EN/TH) ทางแก้ที่คิดไว้: บนจอแคบให้กล่อง Sam อยู่ด้านล่างเหมือน Rex แล้วเช็กว่าไม่ทับล็อบบี้

กฎโครง: ชั้นวาด (`render/`) และ `ui/` อ่านได้แค่ `OfficeStore` กับ `OfficeEvent` — ห้ามรู้ว่าใครขับ (mock หรือ agent จริง)
Source ใหม่ (orchestrator จริง) ต้อง implement `OfficeSource` และส่ง event ชุดเดียวกัน

## กฎเฉพาะของโปรเจกต์นี้

- ใช้เฉพาะทรัพยากรที่ฟรีและไม่ผูกบัตร (ตามธรรมนูญข้อ 4)
- สไปรต์/เสียง/ฟอนต์ ต้องเป็นชุดที่อนุญาตให้ใช้เชิงพาณิชย์ได้ (เช่น CC0) เพราะอาจขายหรือแจกจ่ายภายหลัง
- จดทุกอย่างที่นำมาใช้ (โมเดล สไปรต์ ไลบรารี + ลิงก์ + ใบอนุญาต) ลง `THIRD-PARTY.md`
- ห้ามฝังหรือแจกจ่ายบัญชี/session ของ Claude ไปกับโปรแกรม ถ้าจะรองรับ Claude ต้องใช้ API key ของผู้ใช้เอง
- ดาวน์โหลดโมเดลหรือไฟล์ใหญ่ (เช่น Ollama, ไฟล์โมเดลหลาย GB) ต้องถามผู้ใช้ก่อนทุกครั้ง พร้อมบอกชื่อ แหล่ง ขนาด
- ห้ามคิดว่าเครื่องผู้ใช้ปลายทางแรงเท่าเครื่องนี้ (i3-12100F, RAM 16 GB, RTX 4060 Ti 8 GB — รันโมเดล 7–8B ได้ทีละ 1–2 งาน)
- เปลี่ยนรูปแบบ "เหตุการณ์กลาง" ต้องอัปเดตทั้งตัวจำลองและชั้นวาดในงานเดียวกัน
- ข้อความที่ผู้ใช้เห็นต้องผ่าน `strings.ts` (en+th) เสมอ ดูหัวข้อ "ภาษา (i18n)"
- ก่อนแก้จุดที่เคยมีปัญหา ดู `bugs.md` (ถ้ามี) ก่อน และจดบั๊กที่แก้จริงทุกครั้ง
