## 2026-09-14 — dropdown `.set` ว่างเปล่าสำหรับ `SelfAwareTrendEA` ทั้งที่มีไฟล์อยู่จริง (`sats_*.set`)

- **อาการ**: ผู้ใช้เลือก EA `SelfAwareTrendEA` แล้ว dropdown `.set` ว่างเปล่า ทั้งที่
  `optimizer/sets/` มีไฟล์ `sats_*.set` อยู่หลายสิบไฟล์ (`sats_best_M5.set`, `sats_stage1_M5.set` ฯลฯ)
  — บั๊กนี้กระทบมาตั้งแต่ตอนพัฒนา 2026-09-12 ไม่ใช่แค่วันนี้ เพิ่งมาเจอเพราะผู้ใช้สร้างไฟล์ `.set`
  ใหม่สำหรับ EA ตัวนี้แล้วลองเปิดโปรแกรมครั้งแรก
- **สาเหตุจริง**: `_strategy_key("SelfAwareTrendEA")` (ตัด prefix `Best*_TF_` และ suffix `EA` ทิ้ง)
  ให้ผลเป็น `"selfawaretrend"` แต่ไฟล์ `.set` ของกลยุทธ์นี้ **ทุกไฟล์**ในโปรเจกต์ตั้งชื่อด้วยนามแฝง
  `"sats_*"` (มาจากคำว่า "Self-Aware Trend System" ที่ใช้เรียกกันในเอกสารของ `smart-ea` และเป็นชื่อ
  โฟลเดอร์ dump `sats_opt` ที่ `CORE_TO_DUMPDIR` ผูกไว้กับ `SelfAwareTrendCore.mqh` อยู่แล้ว) —
  `"selfawaretrend"` ไม่ใช่ substring ของ `"sats_..."` เลย `list_sets_for_ea` จึงกรองออกหมด
  คืน list ว่างเสมอ ไม่ว่าจะมีไฟล์เท่าไหร่ก็ตาม
- **วิธีแก้**: เพิ่ม `config._dump_nickname(ea_name)` อ่าน `#include "...Core.mqh"` จากไฟล์ EA จริง
  แล้ว lookup `CORE_TO_DUMPDIR` ตัด `_opt` ออก ได้นามแฝง `"sats"` — `list_sets_for_ea` เช็คทั้ง
  `_strategy_key` และ `_dump_nickname` (union ของทั้งสอง) ไม่ใช่แค่ตัวเดียว
- **บทเรียน**: เวลามีชื่อเล่น/นามแฝงของกลยุทธ์ที่ต่างจากชื่อไฟล์โค้ดจริง (Pine ต้นฉบับชื่อ
  "Self-Aware Trend System" ย่อ SATS, โค้ด MQL5 ตั้งชื่อไฟล์ตามคำเต็ม) การ derive ชื่อกลยุทธ์จาก
  "ตัดคำนำหน้า/ต่อท้ายของชื่อไฟล์" อย่างเดียวไม่พอ ต้องเช็คว่ามี mapping นามแฝงอื่นที่ระบบรู้จักอยู่
  แล้วหรือเปล่า (ในกรณีนี้คือ `CORE_TO_DUMPDIR` ที่มีอยู่แล้วเพื่อจุดประสงค์อื่น) แล้วใช้ร่วมกันแทนที่จะ
  พึ่ง regex เดาชื่อไฟล์อย่างเดียว — ก่อนเพิ่ม EA ใหม่ที่มีชื่อเล่นต่างจากชื่อไฟล์ ให้เช็คว่า `.set`
  ที่จะสร้างตั้งชื่อตรงกับ `_strategy_key` หรือ `_dump_nickname` ตัวใดตัวหนึ่งจริง ไม่งั้นจะเจอปัญหา
  เดียวกันซ้ำแบบเงียบๆ (list ว่างเปล่า ไม่มี error ใดๆ)

## 2026-09-12 — `.set` เดาอัตโนมัติผิด TF เมื่อ EA เป็น M5 แต่มีไฟล์ M15 อยู่ด้วย

- **อาการ**: `config.guess_set_for_ea` เลือกไฟล์ `.set` ผิด timeframe ให้ (เช่น EA ที่ควรใช้
  `amdpo3_clean2025_M5.set` กลับได้ `..._M15.set`)
- **สาเหตุ**: เรียงชื่อไฟล์ตามตัวอักษร "M15" มาก่อน "M5" เสมอ (ตัวอักษร `'1' < '5'`) ถ้าไม่กรองด้วย
  TF ที่ตรงกันเป๊ะ จะหยิบไฟล์แรกตามลำดับตัวอักษรซึ่งผิด และ regex ที่ตัด prefix ชื่อ TF ต้องเรียง
  alternation ยาวไปสั้น (`M15` ก่อน `M1`) ไม่งั้นจะจับได้แค่ "M1" ในคำว่า "M15" แล้วเหลือเศษ "5_..." ค้าง
- **วิธีแก้**: กรองรายการไฟล์ด้วย TF ที่ตรงกันเป๊ะก่อนเสมอ ไม่ใช่แค่ชื่อกลยุทธ์ตรง — ดู
  `src/config.py` (`guess_set_for_ea`)

## 2026-09-12 — เขียนทับ `.set` เพื่อนบ้านเพี้ยนทั้งไฟล์ตอน apply risk override

- **อาการ**: พารามิเตอร์ใน `.set` ที่ไม่เกี่ยวกับความเสี่ยงเลย (เช่น `InpCompressionPct`) ได้ค่าเป็น

- **วิธีแก้**: บังคับให้ทั้ง 3 ฟังก์ชันรับ list ค่าที่ตัด `config.PARAM_PREFIX_COLS` (2 คอลัมน์แรก)

## 2026-09-12 — ปุ่ม "รันทุก .set" พังทุกครั้งด้วย `ValueError: Invalid format string`

- **อาการ**: กดปุ่ม "รันทุก .set ของ EA นี้" รันจนจบ subprocess ครบทุกขั้น (exit code 0 หมด) แต่พอจะ
  สร้างรายงานกลับ error `Invalid format string` ทั้งรายงานเดี่ยวของแต่ละชุดและหน้าเทียบผลรวม
- **สาเหตุ**: `report.write_report` เรียก `time.strftime('%Y%m%d_%H%M%S_%f')` เพื่อกันชื่อไฟล์ชนกัน
  ตอนเขียนรายงานติดกันหลายไฟล์ในไม่กี่วินาที — แต่ `%f` (ไมโครวินาที) เป็น directive ของ
  `datetime.strftime` เท่านั้น ไม่ใช่ของ `time.strftime` ซึ่งบน Windows C runtime จะ raise
  `ValueError: Invalid format string` ทันทีที่เจอ `%f` ที่ไม่รู้จัก (บน Linux/Mac บางระบบอาจรอดเงียบๆ
  แต่ได้ผลลัพธ์ผิดแทน ไม่ raise — พังแค่บน Windows)
- **วิธีแก้**: เปลี่ยนไปใช้ `datetime.now().strftime(...)` (module `datetime` ไม่ใช่ `time`) ใน
  `src/report.py` (`write_report`) — จำไว้: **ห้ามใช้ `%f` กับ `time.strftime`/`time.strptime` เด็ดขาด
  ต้องใช้ `datetime.strftime` เท่านั้นถ้าต้องการความละเอียดระดับไมโครวินาที**

## 2026-09-12 — จูน `SmcEA` แล้ว "ไม่มีผล holdout" ทุก `.set` (ทั้งที่ EA ไม่มีบั๊ก)

- **อาการ**: รัน `.set` ทั้ง 6 ไฟล์ของ `SmcEA` (M5) ผ่าน ea-tuner แล้วได้ "ไม่มีผล holdout" ทุกไฟล์
  ไม่มีแม้แต่ผลรอบ genetic เลยสักชุด ทั้งที่กริดกว้างและลองหลายพารามิเตอร์
- **สาเหตุ**: `config.py` มี `CORE_TO_DUMPDIR` แม็ปชื่อไฟล์ `<Strategy>Core.mqh` ไปยังโฟลเดอร์ที่
  `DumpPass()` ของกลยุทธ์นั้นเขียนผลจริงลง `<Terminal Common>\Files\<dump_dir>\` — ตอนเพิ่ม `SmcEA`
  ไม่ได้เพิ่ม `"SmcCore.mqh": "smc_opt"` เข้าไปในแม็ปนี้ `list_eas()` เลย fallback ไปใช้
  `"unknown_opt"` (`CORE_TO_DUMPDIR.get(core_name, "unknown_opt")`) ทำให้ `run-opt.ps1` ไปหาไฟล์ CSV
  ผลลัพธ์ผิดโฟลเดอร์ (`unknown_opt\` แทนที่จะเป็น `smc_opt\` ที่ EA เขียนจริง) เจอ 0 ไฟล์เสมอ ไม่ว่า
  EA จะเทรดได้จริงกี่ไม้ก็ตาม — ไม่ใช่บั๊กของตรรกะเทรดใน `SmcCore.mqh` เลย
- **วิธีแก้**: เพิ่ม `"SmcCore.mqh": "smc_opt"` เข้า `CORE_TO_DUMPDIR` ใน `src/config.py` ให้ตรงกับ
  path ที่ `DumpPass()` ใน `smart-ea/src/SmcCore.mqh` เขียนจริง (`"smc_opt\\" + stem + ".csv"`)
- **บทเรียน**: ทุกครั้งที่เพิ่ม EA/กลยุทธ์ใหม่ในฝั่ง `smart-ea` ต้องเช็คว่า `ea-tuner/src/config.py` มี
  entry ใน `CORE_TO_DUMPDIR` ตรงกับชื่อไฟล์ Core.mqh นั้นแล้วหรือยัง (เช็ค path ใน `DumpPass()` ของ
  ไฟล์ Core นั้นตรงๆ) ไม่งั้นจะเห็นผลเป็น "ไม่มีผล holdout"/0 trades ทุกกรณีซึ่งดูเหมือน EA มีบั๊ก
  ทั้งที่จริงๆ แค่หาไฟล์ผิดที่
