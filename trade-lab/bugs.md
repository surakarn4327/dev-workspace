## 2026-09-05 — ⭐ ระบบ "หา edge เจอ" บนข้อมูลสุ่ม (บั๊กสำคัญที่สุดจนถึงตอนนี้)

**อาการ** — รัน pipeline บนข้อมูล random walk ที่ *ไม่มี* edge อยู่จริงเลย แล้วได้เงื่อนไข
"ทำกำไร" ที่ผ่านแม้เกณฑ์ Bonferroni ถึง 3 ข้อ ทั้งหมดเป็น `prior_periods.prev_m_*`

**สาเหตุ** — สถิติคิดว่าจำนวน**แท่ง**คือจำนวนตัวอย่างอิสระ ซึ่งผิดมหันต์ ตัวอย่างที่ชัดสุด:

| เงื่อนไข | แท่งที่เลือก | โอกาสที่เกิดจริง |
|---|---|---|
| `clock.is_friday` | 2,016 | **7 วันศุกร์** |
| `prev_m_low_dist <= q10` | 487 | **19 ครั้ง** |

เงื่อนไขพวกนี้ไม่ได้บรรยาย "สภาพตลาด" มันบรรยาย "ช่วงวันที่" — และใน random walk ช่วงเวลา
ต่อเนื่องช่วงหนึ่งย่อมมี drift แรงได้ง่ายๆ พอคิด p-value จาก n=2,016 แทน n=7 ช่วงความเชื่อมั่น
แคบลงประมาณ 17 เท่า noise ธรรมดาก็กลายเป็น p=0.001

ปัญหาเดียวกันเกิดกับ **trade ที่ทับซ้อนกัน** ด้วย: ถือไม้ 120 แท่ง แล้วเข้า 2 ไม้ห่างกัน 5 แท่ง
นั่นไม่ใช่ 2 ตัวอย่าง มันคือ path เดียวที่ถูกนับ 2 ครั้ง

รู้ได้เพราะเขียนสคริปต์ diagnostic นับ "จำนวนช่วงต่อเนื่อง" ของทุกเงื่อนไขออกมาดู
ตามกฎ "ห้ามเดา ต้องตรวจจริง" — เห็นทันทีว่าตัวที่ชนะมี 7-20 ช่วง ขณะที่ตัวปกติมี 2,832 ช่วง

**วิธีแก้** — เพิ่ม [`analysis/episodes.py`](src/tradelab/analysis/episodes.py) แล้วเดินสองทาง:

1. **นับ episode ไม่ใช่แท่ง** — ช่วงต่อเนื่องที่ห่างกันน้อยกว่า `max_hold_bars` ถูกรวมเป็น
   episode เดียว แล้วคำนวณ SE / CI / p-value จาก**ค่าเฉลี่ยของแต่ละ episode**
   (cluster-robust) ไม่ใช่จากทุกแท่ง
2. **ตัดเงื่อนไขที่มี episode น้อยกว่า `min_episodes` (30) ทิ้งเลย** — ไม่รายงานเป็น finding

ผลหลังแก้: เงื่อนไขที่ "รอด" บนข้อมูลสุ่ม = **0** ทั้งฝั่ง Buy และ Sell
มี regression test คุมไว้แล้ว (`test_no_profitable_rule_survives_on_random_data`)

**บทเรียน** — `n` ที่ใช้คิดสถิติในงานข้อมูลราคาแทบไม่เคยเท่าจำนวนแท่ง ถ้าเจอเงื่อนไขที่ดู
ดีเกินจริง ให้ถามก่อนเลยว่า **"มันเกิดขึ้นแยกกันจริงกี่ครั้ง"**

## 2026-09-05 — แถวที่ "มีนัยทางสถิติ" แต่ E[R] ติดลบ

**อาการ** — ในรายงาน มีแถวที่ติดธง `passes_fdr` ✅ แต่คอลัมน์ E[R] เป็น `-0.0179`
คือระบบบอกว่า "มีนัยว่ากำไร" ทั้งที่ตัวเลขบอกว่าขาดทุน

**สาเหตุ** — หลังแก้บั๊กข้างบน `mean_r` กับ `p_value` คิดจาก**คนละฐาน**:
- `mean_r` = ค่าเฉลี่ยถ่วงน้ำหนักตาม**จำนวนไม้** (คือเงินที่ได้จริง)
- `p_value` = ทดสอบจาก**ค่าเฉลี่ยของแต่ละ episode** (ถ่วงน้ำหนักเท่ากันทุก episode)

episode ที่ยาวไม่เท่ากันทำให้สองค่านี้ต่างกันได้ และต่างกันจนคนละเครื่องหมายก็ได้

**วิธีแก้** — รายงานทั้งสองค่า (`mean_r` และ `mean_r_episode`), ย้าย CI ให้อยู่กึ่งกลางที่
`mean_r_episode` (ตัวเดียวกับที่ทดสอบ) และเพิ่มคอลัมน์ **`survives`** ที่ต้องผ่านครบทุกข้อ:
ผ่าน FDR · `mean_r > 0` · `mean_r_episode > 0` · `ci_low > 0` · ไม่พึ่งกำไรจากไม้เดียว
รายงานใช้คอลัมน์นี้เป็นตัวหลัก ไม่ใช้ `passes_fdr` เดี่ยวๆ อีก

**บทเรียน** — เวลาเปลี่ยนวิธีคิด p-value ต้องเช็คว่า "ตัวเลขที่โชว์" กับ "ตัวเลขที่ทดสอบ"
ยังเป็นตัวเดียวกันอยู่มั้ย ไม่งั้นรายงานจะขัดแย้งกันเองแบบเงียบๆ

## 2026-09-05 — baseline ของ reversal/bounce ผิดกลุ่ม ทำให้แจก lift ฟรี

**อาการ** — บนข้อมูลสุ่ม `liquidity.sweep_high_depth_atr >= q90` ได้ lift **5.17 เท่า**
สำหรับเหตุการณ์ "เด้ง" (11.4% vs baseline 2.2%) และ p=1.2e-05 ดูเป็น edge ชัดเจน

**สาเหตุ** — ไม่ใช่การทำนาย แต่เป็น**นิยามซ้อนกันเอง** label `reversal`/`bounce` ถูกนิยามให้
เกิดได้**เฉพาะที่จุด swing** เท่านั้น แต่ baseline คิดจาก**ทุกแท่ง** ดังนั้น feature อะไรก็ตาม
ที่แค่บอกเป็นนัยว่า "ตอนนี้อยู่ที่จุด swing" (ซึ่ง sweep คือตรงตัวเลย — ราคาแทงทะลุ swing เดิม)
จะได้ lift สูงฟรีๆ โดยไม่มีข้อมูลทำนายอะไรเลย

**วิธีแก้** — เพิ่ม `events.family_universe()` แล้วให้:
- `reversal` / `bounce` → เทียบกับ**จุด swing ทั้งหมด** เท่านั้น
- `expansion` → เทียบกับทุกแท่ง (เพราะเกิดได้ทุกที่จริง)

**บทเรียน** — ทุกครั้งที่ตั้ง label ต้องถามว่า "label นี้เกิดได้ที่ไหนบ้าง" แล้วใช้ที่นั่นเป็น
baseline ไม่ใช่ใช้ทุกแท่งเป็น baseline โดยอัตโนมัติ

## 2026-09-05 — sanity check ตรวจสองด้าน ทั้งที่ควรตรวจด้านเดียว

**อาการ** — M1 fail sanity check โดยขาดทุน -0.4192R เทียบกับที่คาด -0.3813R (gap -0.0379R)
ทั้งที่ M5 ผ่านสบาย

**สาเหตุ** — สูตรที่คาด `-(ต้นทุน)/(ระยะ SL)` เป็นการประมาณแบบเชิงเส้น แต่ความจริงต้นทุน
เข้าไม้ทำให้ระยะถึง stop สั้นลง**และ**ระยะถึง TP ไกลขึ้นพร้อมกัน ผลรวมจึงแรงกว่าเชิงเส้น
ยิ่งอัตราส่วนต้นทุน/stop สูง (M1 = 0.36R) ยิ่งเพี้ยนมาก — **ขาดทุนมากกว่าที่คาดคือเรื่องปกติ**
สิ่งที่เป็นไปไม่ได้คือขาดทุน**น้อยกว่า**ที่คาด (นั่นแปลว่า look-ahead หรือลืมหักต้นทุน)

**วิธีแก้** — เปลี่ยนเป็นตรวจด้านเดียว: fail เมื่อ `observed > expected + allowance` เท่านั้น
และแยก check ประเภท "advisory" (`blocking=False`) ออกจาก "correctness" — เพิ่ม
`cost_burden_check` ที่รายงานว่าต้นทุนกินระยะ SL กี่ % โดยไม่ทำให้ study หยุด

**ผลพลอยได้ที่มีค่า** — ตัวเลขนี้บอกความจริงสำคัญเรื่องหนึ่ง: บน **M1** ต้นทุน = **0.36R**
ต่อไม้ ก่อนเทรดจะเริ่มด้วยซ้ำ (M5 = 0.16R) กลยุทธ์บน M1 ต้องเก่งกว่า M5 มากเพื่อผลลัพธ์เท่ากัน

**บทเรียน** — sanity check ที่ตรวจสองด้านจะ fail จากการประมาณของตัวเองบ่อยๆ
ถามก่อนว่า "ทิศทางไหนที่เป็นไปไม่ได้จริง" แล้วตรวจแค่ทิศนั้น

## 2026-09-05 — `shift()` บน boolean Series ทำให้ dtype กลายเป็น object เงียบๆ

**อาการ** — `IndexError: arrays used as indices must be of integer (or boolean) type`
ตอนกำหนด label เหตุการณ์ (`event[bounce_up] = BOUNCE_UP`) ทั้งที่บรรทัดก่อนหน้าหน้าตาเหมือนกัน
แต่ผ่านได้

**สาเหตุ** — `swing_pivots()` ทำ `is_ph.shift(w).fillna(False)` — `shift()` บน bool Series
ใส่ NaN เข้ามา (NaN ไม่ใช่ bool) pandas จึงเปลี่ยน dtype เป็น **object** พอ `.to_numpy()`
ได้ array dtype object แล้ว `&` กับ bool array ก็ได้ object array ซึ่งใช้เป็น index ไม่ได้
บรรทัด `exp_up` ผ่านเพราะไม่มี `at_swing_*` ผสมอยู่

**วิธีแก้** — `.fillna(False).astype(bool)` ที่ต้นทางใน `swing_pivots()` และ
`.to_numpy(dtype=bool)` ที่จุดใช้งานใน `events.detect()`

**บทเรียน** — `shift()` / `reindex()` / `fillna()` บน bool Series ใน pandas ทำให้เป็น object
ได้ทุกครั้ง ต้อง `.astype(bool)` ปิดท้ายเสมอ — ตัวที่อันตรายคือมันไม่ error ตรงจุดที่เกิด
แต่ไป error ที่อื่นไกลๆ (หรือแย่กว่านั้น: ไม่ error เลย แต่คำนวณผิด)

## 2026-09-05 — drawdown คิดจากจุดเริ่มผิด

**อาการ** — ชุดผลลัพธ์ `[-1R, -1R, +10R]` รายงาน max drawdown = 1.0R ทั้งที่ขาดทุนสะสม
จริงไป 2R ก่อนจะกลับมา

**สาเหตุ** — `peak = np.maximum.accumulate(cumsum(r))` ทำให้ค่า peak เริ่มที่ผลลัพธ์ไม้แรก
(-1) ไม่ใช่ที่ 0 กลยุทธ์ที่ขาดทุนตั้งแต่ไม้แรกจะรายงาน DD ต่ำกว่าจริงเสมอ

**วิธีแก้** — ต่อ 0 ไว้หน้า equity curve: `np.concatenate(([0.0], np.cumsum(r)))`

**บทเรียน** — DD เป็นตัวเลขที่ผู้ใช้ตัดสินใจจากมันจริง ผิดทางต่ำ = อันตรายกว่าผิดทางสูง
