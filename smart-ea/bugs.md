## 2026-09-04 — compile error รัวๆ (24 errors, 20 warnings) ตอนเขียน EA ตัวแรก

(บั๊กนี้เจอบน `SmartEA_XAUUSD.mq5` ซึ่งถูกลบไปแล้วตอนเคลียร์โปรเจกต์ 2026-09-07
แต่บทเรียนใช้กับ MQL5 ทุกไฟล์ จึงเก็บไว้)

**อาการ**: MetaEditor compile แล้วขึ้น error กระจายทั้งไฟล์ "open parenthesis expected", "implicit conversion from 'number' to 'string'" ตั้งแต่บรรทัด 31 เป็นต้นไป ดูเหมือนพังทั้งไฟล์

**สาเหตุจริง**: ประกาศตัวแปร `const string SymbolName = "XAUUSDm"` ชื่อชนกับฟังก์ชัน built-in ของ MQL5 คือ `SymbolName()` (คืนชื่อ symbol จาก index) — error แรกสุดคือ "identifier 'SymbolName' already used, built-in 'SymbolName'" ส่วน error ที่เหลือทั้งหมดเป็นผลพวง parser สับสนจากตัวนี้ตัวเดียว ไม่ใช่ error จริงหลายจุด

**วิธีแก้**: เปลี่ยนชื่อตัวแปรเป็น `TradeSymbol` แทน (sed แทนที่ทั้งไฟล์) compile ผ่านสะอาด

**บทเรียน**: ก่อนตั้งชื่อ const/variable ใน MQL5 เช็คก่อนว่าชนกับ built-in function ชื่อเดียวกันไหม (เช่น `Symbol`, `SymbolName`, `Bid`, `Ask`, `Point` เป็นชื่อที่เสี่ยงชน) — ถ้า compile error เยอะผิดปกติกระจายทั้งไฟล์ ให้ดู error **แรกสุด** ก่อน มักเป็นต้นตอเดียวที่ทำให้ error หลอกอื่นๆ ตามมา ไม่ต้องไล่แก้ทีละบรรทัด

## 2026-09-04 — Lot size คำนวณผิด เสีย/ได้เงินจริงเล็กกว่าที่ตั้งใจ ~10 เท่า

**อาการ**: backtest เดือน ส.ค. 2026, ตั้ง `InpRiskPerTrade=200` (ตั้งใจให้เสีย ~$200/ไม้) แต่ผล backtest average loss trade = **-$19.69** เท่านั้น (ควรใกล้ 200)

**สาเหตุจริง**: `CalcLot()` ใน [src/SmartEA_XAUUSD.mq5](src/SmartEA_XAUUSD.mq5) ดึง `SymbolInfoDouble(TradeSymbol, SYMBOL_POINT)` มาหาร SL distance เพื่อได้ "จำนวนจุด" — แต่ **XAUUSDm ของ Exness ราคาแสดงทศนิยม 3 ตำแหน่ง (เช่น 4471.501) แปลว่า `SYMBOL_POINT` จริงของ broker คือ 0.001** ในขณะที่สูตร lot ที่ผู้ใช้ออกแบบไว้ (ตัวอย่าง: SL distance 4.700 = "470 จุด") ตั้งใจนิยาม 1 "จุด" = 0.01 เสมอ (ไม่ใช่ tick size จริงของ broker) — โค้ดใช้ point ของ broker (0.001) แทนที่จะ hardcode 0.01 ตามนิยามของผู้ใช้ ทำให้ sl_points คำนวณออกมาใหญ่กว่าที่ตั้งใจ 10 เท่า → lot เล็กลง 10 เท่า → เงินเสีย/ได้จริงเล็กกว่าที่ตั้งใจ 10 เท่า

**วิธีแก้**: เพิ่ม `const double RiskPointUnit = 0.01;` แล้วใช้ค่านี้แทน `SymbolInfoDouble(...,SYMBOL_POINT)` ในสูตร lot โดยเฉพาะ (ไม่ใช่ tick size จริงของ broker) — หลัง fix backtest เดือนเดิม average loss = -205.66, average profit = 395.71 ตรงตามที่ตั้งใจ (risk≈200, RR≈2)

**บทเรียน**: **ห้ามสมมติว่า "จุด" ที่ user พูดถึง (ในสูตรธุรกิจ/risk management) เท่ากับ `SYMBOL_POINT` ของ broker เสมอไป** โดยเฉพาะ instrument ที่ราคาแสดงทศนิยมมากกว่าปกติ (เช่น gold บาง broker ใช้ 2 ทศนิยม บาง broker ใช้ 3) ต้องถามหรือ derive หน่วย "จุด" จากตัวอย่างตัวเลขจริงที่ user ให้มาก่อน ไม่ใช่ผูกกับค่า broker ตรงๆ — ถ้าตัวเลขผลลัพธ์ (P&L จริง) ต่างจากที่ตั้งใจเป็นสิบเท่า/ร้อยเท่า ให้สงสัยเรื่อง unit mismatch (point/pip/tick) ก่อนอย่างอื่น

## 2026-09-10 — พาเนลบนชาร์ตขึ้นคำว่า "Label" เต็มไปหมด

**อาการ**: หลังเพิ่มพาเนลสรุปให้ `MARibbonEA` รัน Strategy Tester แบบ visual แล้วมุมขวาบนขึ้นคำว่า
`Label` กระจาย 15 จุด แทนที่จะว่างเปล่า (แถวหัวตารางกับแถว "สัญญาณ" แสดงข้อความถูกต้องปกติ)

**สาเหตุจริง**: ตอนยังไม่มีไม้เปิดอยู่ โค้ดสั่ง `PanelRow(r, "", "", "", ...)` เพื่อ "ล้างแถว" ซึ่งไปตั้ง
`ObjectSetString(0, name, OBJPROP_TEXT, "")` — **MT5 ไม่ยอมให้ OBJ_LABEL มีข้อความว่าง จะแทนที่ด้วย
คำ default `"Label"` ให้เอง** ไม่ใช่ปัญหาตำแหน่ง/คอร์เนอร์อย่างที่ดูเผินๆ (แถวที่มีข้อความจริงวางถูกตำแหน่ง
อยู่แล้ว) สังเกตได้จากจำนวน: 5 แถวว่าง x 3 คอลัมน์ = 15 ตรงกับจำนวน `Label` ที่เห็นพอดี

**วิธีแก้**: ใน `PanelRow()` ของ [src/MARibbonEA.mq5](src/MARibbonEA.mq5) ถ้าข้อความของคอลัมน์นั้นเป็น
ค่าว่าง ให้ `ObjectDelete` ทิ้งแทนการตั้งข้อความ — ซ่อน OBJ_LABEL ด้วยการลบเท่านั้น

**บทเรียน**: **ห้ามใช้ข้อความว่างเป็นวิธีซ่อน OBJ_LABEL ใน MT5** ต้องลบ object หรือใช้
`OBJPROP_TIMEFRAMES = OBJ_NO_PERIODS` และเวลาเจอข้อความประหลาดซ้ำๆ บนชาร์ต ให้นับจำนวนที่เห็น
เทียบกับจำนวน object ที่โค้ดสร้าง มักชี้ตัวการได้ทันทีโดยไม่ต้องไล่โค้ดทีละบรรทัด

## 2026-09-10 — run-opt.ps1 พังทั้งไฟล์ ขึ้น Unexpected token รัวๆ ทั้งที่โค้ดถูก

**อาการ**: รัน `.\run-opt.ps1` แล้ว PowerShell ขึ้น ParserError หลายจุด `Unexpected token`,
`Missing closing '}'` โดยข้อความ error โชว์คอมเมนต์ภาษาไทยเป็นตัวอักษรขยะ (`เน€เธเธ...`)
ทั้งที่เปิดไฟล์ดูแล้วโค้ดถูกต้องปกติ

**สาเหตุจริง**: ไฟล์ถูกเขียนเป็น UTF-8 **ไม่มี BOM** — Windows PowerShell 5.1 (`powershell.exe`
ไม่ใช่ `pwsh`) อ่านไฟล์ `.ps1` เป็น **ANSI codepage เสมอถ้าไม่มี BOM** ตัวอักษรไทยจึงถูกตีความผิด
กลายเป็นอักขระที่ parser มองว่าเป็น token แปลกปลอม ไม่เกี่ยวกับโครงสร้างโค้ดเลย

**วิธีแก้**: บันทึกไฟล์ใหม่เป็น UTF-8 **พร้อม BOM**

`[System.IO.File]::WriteAllText(C:\dev\smart-ea\bugs.md, , [System.Text.UTF8Encoding]::new($true))`

**บทเรียน**: **สคริปต์ `.ps1` ที่มีตัวอักษรไทย (หรือ non-ASCII ใดๆ) ต้องมี BOM เสมอ** ถ้าจะให้
`powershell.exe` รันได้ — เครื่องมือเขียนไฟล์ส่วนใหญ่ default เป็น UTF-8 ไม่มี BOM ซึ่งใช้ไม่ได้
สังเกตอาการได้จาก **ตัวอักษรขยะในข้อความ error** ถ้าเห็นแบบนี้ให้สงสัย encoding ก่อน อย่าไปไล่แก้
วงเล็บหรือ syntax เพราะโค้ดไม่ได้ผิด

## 2026-09-10 — รอบที่ไม่ได้รันจริง กลับรายงานผลสำเร็จ พร้อมตัวเลขของรอบก่อน

**อาการ**: สั่ง optimization ก้อนที่สอง (ribbon shift 9-20 ของ M5) สคริปต์รายงานว่าเสร็จ เก็บผลได้
48 ชุด แต่พอเปิดดูกลับเป็น shift -3 ถึง 8 ซึ่งเป็นช่วงของก้อนแรกทั้งหมด

**สาเหตุจริง**: สองอย่างซ้อนกัน
1. สั่งรันด้วย `Start-Job` ซึ่งตายไปพร้อม shell ของ tool call — MT5 จึงไม่เคยถูกเรียกเลย
2. `run-opt.ps1` ล้างโฟลเดอร์ผลลัพธ์ **ตอนเริ่ม** อย่างเดียว ไม่ได้ล้างตอนจบ ไฟล์ของก้อนแรก
   จึงยังค้างอยู่ พอขั้นตอนเก็บผลทำงาน มันเลยหยิบไฟล์เก่ามารายงานเป็นผลของรอบใหม่

ข้อ 2 คือตัวที่อันตราย เพราะทำให้ "ไม่ได้รัน" กับ "รันแล้วสำเร็จ" ให้ผลลัพธ์หน้าตาเหมือนกันเป๊ะ

**วิธีแก้**: ล้างโฟลเดอร์ผลลัพธ์หลังเก็บด้วย ไม่ใช่แค่ตอนเริ่ม และเลิกใช้ `Start-Job` สั่งงานยาว
ให้ใช้ `run_in_background` ของ tool แทน

**บทเรียน**: **ขั้นตอนที่รวบรวมผลลัพธ์ต้องแยกให้ออกระหว่าง "ไม่มีผล" กับ "ผลของรอบก่อน"** ถ้าที่เก็บ
ผลลัพธ์เป็นที่เดิมทุกรอบ ต้องล้างทั้งก่อนและหลัง ตรวจง่ายๆ ด้วยการดูว่าค่าพารามิเตอร์ในผลตรงกับ
ช่วงที่สั่งไปหรือเปล่า — ถ้าไม่ตรง แปลว่ากำลังอ่านของเก่าอยู่

## 2026-09-11 — รอบไล่หาช่วงเวลาเทรด 42 ชุด เหลือผลชุดเดียว

**อาการ**: สั่ง optimization ไล่ `InpHourFrom` x `InpHourTo` 42 ชุดบน `RangeFadeEA`
สคริปต์รายงานว่าเสร็จปกติ ไม่มี error แต่ไฟล์ผลมีแถวเดียว

**สาเหตุจริง**: `DumpPass()` ตั้งชื่อไฟล์ผลจากค่าพารามิเตอร์ (1 pass = 1 ไฟล์ เพื่อไม่ให้
agent ที่รันขนานกันเขียนชนกัน) แต่ **ชื่อไฟล์ไม่มี `InpHourFrom`/`InpHourTo` อยู่ในนั้น**
ทั้ง 42 ชุดจึงได้ชื่อไฟล์เดียวกันเป๊ะ แล้วเขียนทับกันจนเหลือชุดสุดท้ายชุดเดียว
ไม่ใช่ปัญหาของ MT5 หรือของ `run-opt.ps1` เลย

**วิธีแก้**: เพิ่มสองตัวนั้นเข้าไปในชื่อไฟล์และในคอลัมน์ CSV ของ
[src/RangeFadeCore.mqh](src/RangeFadeCore.mqh) แล้วรันรอบนั้นใหม่ (ผังคอลัมน์ของ
RangeFade จึงเป็น 35 ช่อง ไฟล์ 33 ช่องที่รันก่อนแก้ใช้ `-Layout rangefade15`)

**บทเรียน**: **พารามิเตอร์ทุกตัวที่ใส่ช่วงค่าใน `.set` ได้ ต้องอยู่ในชื่อไฟล์ผลด้วยเสมอ**
ไม่งั้นชุดที่ต่างกันจะทับกันเงียบๆ โดยไม่มีอะไรฟ้อง — ตรวจง่ายๆ ทุกครั้งด้วยการเทียบ
**จำนวนแถวในไฟล์ผล กับจำนวนชุดที่คำนวณจากช่วงค่าที่สั่งไป** ถ้าน้อยกว่า ให้สงสัยชื่อไฟล์ชนกันก่อน
(อาการเดียวกับบั๊ก 2026-09-10 เรื่องผลค้างของรอบก่อน คือ "ไม่ได้รัน" กับ "รันแล้ว" หน้าตาเหมือนกัน)

## 2026-09-11 — optimization รันแบบ exhaustive เต็มกริด (268,800 ชุด, ETA 40 ชม.) ทั้งที่ตั้งใจให้ genetic

**อาการ**: สั่ง `run-opt.ps1` ไล่กริดกว้าง (9 พารามิเตอร์ ~270k combos) โดยไม่ได้ส่ง `-Optimization`
มาเอง (ใช้ default `'1'`) Strategy Tester GUI โชว์ "Slow complete algorithm" และ ETA 40:51:05

**สาเหตุจริง**: ไม่ใช่บั๊ก — `run-opt.ps1` ตั้ง default `$Optimization = '1'` ("ไล่ครบ") ไม่ใช่ genetic
ต้องส่ง `-Optimization 2` เองทุกครั้งถ้าต้องการ genetic sampling ("Fast genetic based algorithm")
ค่า `1` เหมาะกับกริดเล็ก (สิบ-ร้อยชุด) เท่านั้น กริดกว้างเกิน ~1,000 combos ต้องใช้ `2` เสมอ
ช่อง GUI "Optimization algorithm" ตอบสนองค่าที่ส่งผ่าน ini ได้จริง ไม่ใช่ GUI-only ตามที่
เอกสารเดิมสงสัยไว้ — เรื่องนี้ตรวจสอบแล้วว่าไม่ใช่ปัญหา reset เหมือนช่องอื่นๆ (Model/ExecutionMode)

**วิธีแก้**: หยุดรอบที่รันผิดทันที (`taskkill /F /IM terminal64.exe`) ลบผลค้าง (partial exhaustive
scan ไม่ใช่ตัวแทนที่ดีของกริดทั้งหมด ห้ามใช้) แล้วสั่งใหม่พร้อม `-Optimization 2`

**บทเรียน**: **ก่อนสั่งกริดใหญ่กว่าพันชุด ต้องส่ง `-Optimization 2` เสมอ อย่าพึ่ง default**
เช็คจำนวน combos ล่วงหน้าจากการคูณจำนวนค่าที่ไล่ในแต่ละพารามิเตอร์ ถ้าเกินหลักพัน ให้แยกจูนเป็น
สเตจย่อย (จูน 2-4 ตัวต่อรอบ ไม่ใช่โยนทุกตัวพร้อมกัน) — วิธีนี้ยังช่วยให้เช็ค neighbor ของผู้ชนะง่ายขึ้นด้วย
เพราะพารามิเตอร์ที่เหลือถูกตรึงไว้คงที่
