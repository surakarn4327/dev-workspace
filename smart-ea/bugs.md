## 2026-09-11 — สั่งกริด SATS ด้วย `-Model 0` (Every tick) แล้วรอบนั้นค้างจนต้อง kill ทิ้ง

**อาการ**: สั่ง `run-opt.ps1` ไล่กริด 80 ชุดบน M5 เต็มปี 2568 พร้อม `-Model 0` (Every tick)
MT5 เปิดขึ้นมาแล้วไม่มี progress log เพิ่มเลยกว่า 4 นาที ไฟล์ผลออกมา 4 ไฟล์ใน 8 นาที
(ประมาณการ = จบใน 2-3 ชั่วโมง) จนผู้ใช้เห็นว่าค้างแล้วสั่ง `taskkill` ทิ้ง

**สาเหตุจริง**: เลือกโมเดล tick ผิด ไม่ใช่บั๊กของสคริปต์ — `run-opt.ps1` มี default `-Model 1`
(`1 minute OHLC`) อยู่แล้วซึ่งเป็นมาตรฐานของทุกรอบ grid ในโปรเจกต์นี้ แต่ไปส่ง `-Model 0` มาเอง
เพราะเข้าใจผิดจากประโยคใน `optimizer/README.md` ที่ว่า "ผลที่เก็บไว้ทั้งหมดใช้ `-Model 0`"
(ประโยคนั้นพูดถึงผลชุดเก่าของ MARibbon ไม่ใช่คำสั่งให้ใช้กับทุกรอบ) Every tick ปั้นจุดระหว่าง
แท่งละเอียดกว่ามาก บน M5 เต็มปีที่เข้าไม้หลักพันไม้ต่อชุดจึงกินทั้งเวลาและแรม
(เครื่องนี้เหลือว่างราว 3 GB) **รอบเดียวกันด้วย `-Model 1` ใช้เวลา 1.2 นาทีจบครบ 80 ชุด**
เร็วกว่าประมาณ 50 เท่า และให้จำนวนแถวครบตามจำนวนชุดที่สั่ง

**วิธีแก้**: สั่งใหม่โดยไม่ส่ง `-Model` เลย (ปล่อย default `1`) — ทุกสเตจของการจูน SATS
หลังจากนั้นใช้ค่านี้ทั้งหมด

**บทเรียน**: **รอบ optimize/grid ทุกรอบใช้ `1 minute OHLC` (default) เสมอ อย่าส่ง `-Model 0`
มาเอง** เก็บ Every tick / real tick ไว้ใช้กับ**รอบรันเดี่ยว**ที่ต้องการความแม่นของลำดับ SL/TP
ภายในแท่งเท่านั้น และถ้าจะเทียบตัวเลขข้ามรอบ ต้องใช้โมเดลเดียวกันทั้งช่วงจูนและช่วงตรวจสอบ —
สังเกตอาการได้เร็วๆ จาก **อัตราไฟล์ผลที่ออกมาต่อนาที** ถ้าช้ากว่าที่ควรเป็นสิบเท่าให้สงสัย
โมเดล tick ก่อนอย่างอื่น อย่านั่งรอเฉยๆ

## 2026-09-11 — จูน SATS ไล่ 80 ชุด (BaseMult × SlAtrMult × CharFlipMinAge) เหลือผล 20 แถว

**อาการ**: สั่งจูน `SelfAwareTrendEA` บน M5 ไล่ 3 พารามิเตอร์ (`InpBaseMult` 5 ค่า × `InpSlAtrMult`
4 ค่า × `InpCharFlipMinAge` 4 ค่า = 80 ชุด) `run-opt.ps1` รายงานว่าเสร็จปกติ ไม่มี error
แต่ไฟล์ผลมีแค่ 20 แถว (= 80 ÷ 4 พอดี)

**สาเหตุจริง**: เหมือนบั๊ก 2026-09-11 ของ `RangeFadeEA` เป๊ะ — `DumpPass()` ใน
[`src/SelfAwareTrendCore.mqh`](src/SelfAwareTrendCore.mqh) ตั้งชื่อไฟล์ผลจากพารามิเตอร์ แต่ใน stem
มีแค่ `age%d` ซึ่งผูกกับ `InpTradeMaxAge` (ค่าคงที่ตลอดการจูนรอบนี้) ไม่ใช่ `InpCharFlipMinAge`
ที่กำลังไล่ค่าจริง — 4 ค่าของ `InpCharFlipMinAge` (5/10/15/20) จึงได้ชื่อไฟล์เดียวกันเป๊ะ (เพราะ
`BaseMult`/`SlAtrMult` เท่ากัน) แล้วเขียนทับกันจนเหลือชุดสุดท้ายชุดเดียวต่อคู่ (BaseMult, SlAtrMult)
= 5×4 = 20 แถวที่เหลือ ไม่ใช่ปัญหาของ MT5 หรือ `run-opt.ps1` เลย (เหมือนเดิม)

**วิธีแก้**: เพิ่ม `InpCharFlipMinAge`, `InpCharFlipHigh`, `InpCharFlipLow`, `InpAsymStrength`
เข้าไปในทั้งชื่อไฟล์และคอลัมน์ CSV ของ `DumpPass()` แล้ว compile + deploy ใหม่ (คอลัมน์พารามิเตอร์
ของ `SelfAwareTrendEA` จึงเพิ่มจาก 14 เป็น 18 ช่อง — ไฟล์ผลที่รันก่อนแก้ (`sats_stage1_M5.csv`,
`SelfAwareTrendEA_*_default.csv`, `SelfAwareTrendEA_*_full.csv`) ยัง 14 ช่องแบบเดิม ห้ามเอามาต่อกัน
ตรงๆ)

**บทเรียน**: **ก่อนไล่กริดพารามิเตอร์ตัวไหนของ EA ในโปรเจกต์นี้ ต้องเปิด `DumpPass()` เช็คก่อนว่า
พารามิเตอร์ตัวนั้นอยู่ในชื่อไฟล์ผลจริงหรือเปล่า** อย่าเชื่อว่าชื่อฟิลด์ในโค้ด (เช่น `age%d`) ตรงกับ
input ที่ตั้งใจส่งมาเสมอ — สายตาไล่จาก `.set` ไป `DumpPass()` ทีละตัวก่อนสั่งรันจริง ไม่ใช่แค่ดูว่า
จำนวนแถวผลตรงกับจำนวนชุดที่คำนวณจากช่วงค่าไหม (ตรวจได้แค่ตอนจบ เสียเวลารันไปแล้วเปล่าๆ)

## 2026-09-04 — compile error รัวๆ (24 errors, 20 warnings) ตอนเขียน EA ตัวแรก

(บั๊กนี้เจอบน `SmartEA_XAUUSD.mq5` ซึ่งถูกลบไปแล้วตอนเคลียร์โปรเจกต์ 2026-09-07
แต่บทเรียนใช้กับ MQL5 ทุกไฟล์ จึงเก็บไว้)

**อาการ**: MetaEditor compile แล้วขึ้น error กระจายทั้งไฟล์ "open parenthesis expected", "implicit conversion from 'number' to 'string'" ตั้งแต่บรรทัด 31 เป็นต้นไป ดูเหมือนพังทั้งไฟล์

**สาเหตุจริง**: ประกาศตัวแปร `const string SymbolName = "XAUUSDm"` ชื่อชนกับฟังก์ชัน built-in ของ MQL5 คือ `SymbolName()` (คืนชื่อ symbol จาก index) — error แรกสุดคือ "identifier 'SymbolName' already used, built-in 'SymbolName'" ส่วน error ที่เหลือทั้งหมดเป็นผลพวง parser สับสนจากตัวนี้ตัวเดียว ไม่ใช่ error จริงหลายจุด

**วิธีแก้**: เปลี่ยนชื่อตัวแปรเป็น `TradeSymbol` แทน (sed แทนที่ทั้งไฟล์) compile ผ่านสะอาด

**บทเรียน**: ก่อนตั้งชื่อ const/variable ใน MQL5 เช็คก่อนว่าชนกับ built-in function ชื่อเดียวกันไหม (เช่น `Symbol`, `SymbolName`, `Bid`, `Ask`, `Point` เป็นชื่อที่เสี่ยงชน) — ถ้า compile error เยอะผิดปกติกระจายทั้งไฟล์ ให้ดู error **แรกสุด** ก่อน มักเป็นต้นตอเดียวที่ทำให้ error หลอกอื่นๆ ตามมา ไม่ต้องไล่แก้ทีละบรรทัด

## 2026-09-04 — Lot size คำนวณผิด เสีย/ได้เงินจริงเล็กกว่าที่ตั้งใจ ~10 เท่า

**อาการ**: backtest เดือน ส.ค. 2026, ตั้ง `InpRiskPerTrade=200` (ตั้งใจให้เสีย ~$200/ไม้) แต่ผล backtest average loss trade = **-$19.69** เท่านั้น (ควรใกล้ 200)

**สาเหตุจริง**: `CalcLot()` ใน [src/SmartEA_XAUUSD.mq5](src/SmartEA_XAUUSD.mq5) ดึง `SymbolInfoDouble(TradeSymbol, SYMBOL_POINT)` มาหาร SL distance เพื่อได้ "จำนวนจุด" — แต่ **XAUUSDm ของ Exness ราคาแสดงทศนิยม 3 ตำแหน่ง (เช่น 4471.501) แปลว่า `SYMBOL_POINT` จริงของ broker คือ 0.001** ในขณะที่สูตร lot ที่ผู้ใช้ออกแบบไว้ (ตัวอย่าง: SL distance 4.700 = "470 จุด") ตั้งใจนิยาม 1 "จุด" = 0.01 เสมอ (ไม่ใช่ tick size จริงของ broker) — โค้ดใช้ point ของ broker (0.001) แทนที่จะ hardcode 0.01 ตามนิยามของผู้ใช้ ทำให้ sl_points คำนวณออกมาใหญ่กว่าที่ตั้งใจ 10 เท่า → lot เล็กลง 10 เท่า → เงินเสีย/ได้จริงเล็กกว่าที่ตั้งใจ 10 เท่า

**วิธีแก้**: เพิ่ม `const double RiskPointUnit = 0.01;` แล้วใช้ค่านี้แทน `SymbolInfoDouble(...,SYMBOL_POINT)` ในสูตร lot โดยเฉพาะ (ไม่ใช่ tick size จริงของ broker) — หลัง fix backtest เดือนเดิม average loss = -205.66, average profit = 395.71 ตรงตามที่ตั้งใจ (risk≈200, RR≈2)

**บทเรียน**: **ห้ามสมมติว่า "จุด" ที่ user พูดถึง (ในสูตรธุรกิจ/risk management) เท่ากับ `SYMBOL_POINT` ของ broker เสมอไป** โดยเฉพาะ instrument ที่ราคาแสดงทศนิยมมากกว่าปกติ (เช่น gold บาง broker ใช้ 2 ทศนิยม บาง broker ใช้ 3) ต้องถามหรือ derive หน่วย "จุด" จากตัวอย่างตัวเลขจริงที่ user ให้มาก่อน ไม่ใช่ผูกกับค่า broker ตรงๆ — ถ้าตัวเลขผลลัพธ์ (P&L จริง) ต่างจากที่ตั้งใจเป็นสิบเท่า/ร้อยเท่า ให้สงสัยเรื่อง unit mismatch (point/pip/tick) ก่อนอย่างอื่น

เทียบกับจำนวน object ที่โค้ดสร้าง มักชี้ตัวการได้ทันทีโดยไม่ต้องไล่โค้ดทีละบรรทัด

## 2026-09-10 — run-opt.ps1 พังทั้งไฟล์ ขึ้น Unexpected token รัวๆ ทั้งที่โค้ดถูก

**อาการ**: รัน `.\run-opt.ps1` แล้ว PowerShell ขึ้น ParserError หลายจุด `Unexpected token`,
`Missing closing '}'` โดยข้อความ error โชว์คอมเมนต์ภาษาไทยเป็นตัวอักษรขยะ (`เน€เธเธ...`)
ทั้งที่เปิดไฟล์ดูแล้วโค้ดถูกต้องปกติ

**สาเหตุจริง**: ไฟล์ถูกเขียนเป็น UTF-8 **ไม่มี BOM** — Windows PowerShell 5.1 (`powershell.exe`
ไม่ใช่ `pwsh`) อ่านไฟล์ `.ps1` เป็น **ANSI codepage เสมอถ้าไม่มี BOM** ตัวอักษรไทยจึงถูกตีความผิด
กลายเป็นอักขระที่ parser มองว่าเป็น token แปลกปลอม ไม่เกี่ยวกับโครงสร้างโค้ดเลย

**วิธีแก้**: บันทึกไฟล์ใหม่เป็น UTF-8 **พร้อม BOM**

`[System.IO.File]::WriteAllText(C:\dev\smart-ea\bugs.md, , [System.Text.UTF8Encoding]::new($true))`

**บทเรียน**: **สคริปต์ `.ps1` ที่มีตัวอักษรไทย (หรือ non-ASCII ใดๆ) ต้องมี BOM เสมอ** ถ้าจะให้
`powershell.exe` รันได้ — เครื่องมือเขียนไฟล์ส่วนใหญ่ default เป็น UTF-8 ไม่มี BOM ซึ่งใช้ไม่ได้
สังเกตอาการได้จาก **ตัวอักษรขยะในข้อความ error** ถ้าเห็นแบบนี้ให้สงสัย encoding ก่อน อย่าไปไล่แก้
วงเล็บหรือ syntax เพราะโค้ดไม่ได้ผิด

"ข้าม" ไปเฉยๆ ไม่เก็บเป็นสัญญาณค้างเหมือนที่ฉบับแก้ก่อนหน้าทำกับ live path — พอ reattach ระหว่างติด
cutoff, replay คำนวณ FSM ใหม่จากศูนย์ ไม่เจอสัญญาณค้างเพราะไม่เคยถูกสอนให้จำ ทำให้สัญญาณหายไปอีกรอบ
เหมือนก่อนแก้เดิมทุกประการ

**วิธีแก้**: [`SatsReplayHistory()`](src/SelfAwareTrendCore.mqh:730) เพิ่มตัวแปรคู่ขนาน
`blockDir/blockEntry/blockSl/blockTp1/blockTp2/blockTp3` แยกจาก `virtDir` (ไม้เสมือนที่เปิดจริงในแบบ
จำลอง) — เวลา replay เจอ flip ระหว่างที่ `cutoffNow` เป็นจริง จะเก็บเป็น `blockDir` แทนการข้ามทิ้ง
ทุกแท่งถัดไปเช็คว่าราคาผ่านโซน entry↔SL ของ `blockDir` หรือยัง (มิเรอร์ `SatsTryCatchup` แต่เช็คระดับ
แท่งแทนระดับ tick) ถ้าผ่านแล้วแปลงเป็น `virtDir` จริงในแบบจำลองต่อ ถ้าจบ replay แล้วยังไม่ผ่าน จะถูก
ส่งเป็น `gPendingDir` เหมือนกรณี `virtDir` ค้างตอนจบ replay เดิม — ก็ยังใช้ `PL_HourBlocked()` ตัวใหม่
(เพิ่มใน [PositionLib.mqh](src/PositionLib.mqh) คู่กับ `PL_PastCutoff`) แทนสูตร `dt.hour>=cutoff` เดิม
ให้ replay กับ live เช็คช่วงเวลาด้วยสูตรเดียวกันเป๊ะ (รวม `InpTradeStartServerHour` ด้วย) compile ผ่าน
ทั้งสองไฟล์ (0 errors) **ยังไม่เคยเห็นผลจริงว่า reattach ระหว่างติด cutoff แล้วสัญญาณรอดจริงตามที่ตั้งใจ**

**บทเรียน**: **state ที่เก็บไว้แค่ใน live path (global variable ธรรมดา) ต้องมี "ทางสร้างใหม่" จาก
history ตอน re-init เสมอ ถ้า EA ตัวไหนออกแบบให้ reload ได้บ่อย (เปลี่ยน tf/symbol/reattach)** —
รอบแก้ที่แล้ว (หัวข้อก่อนหน้า) แก้แค่ครึ่งเดียว (เพิ่ม state ใหม่แต่ไม่เพิ่มการ "จำลองสร้าง state นั้นใหม่"
ใน replay) ทำให้ดูเหมือนแก้เสร็จ (compile ผ่าน, มี log ยืนยัน) แต่พอ reload จริงกลับไม่ทำงาน — ทุกครั้งที่
เพิ่ม global state ใหม่ให้ live path ต้องถามตัวเองเสมอว่า "ถ้า EA reload ตอนนี้พอดี state นี้จะหายไหม
แล้ว replay จะสร้างมันขึ้นมาใหม่ได้ไหม" ไม่ใช่แค่ทดสอบ path เดียวที่ EA ไม่ได้ reload

ต้องรอเจอสถานการณ์แบบเดิมอีกครั้งถึงจะยืนยันได้ 100%

**บทเรียน**: **replay/simulation ที่มองไม่เห็น state จริงของโลกภายนอก (บัญชีจริง) จะสร้าง state ปลอม
ที่ "ดูเหมือนถูกต้อง" ได้เสมอ เพราะมันคำนวณด้วยสูตร+ข้อมูลเดียวกับของจริง** — จุดอันตรายไม่ได้อยู่ที่ตอน
สร้าง state ปลอมนั้น (ตอนนั้นดูไม่มีพิษภัย เพราะ guard อื่นกันไว้อยู่) แต่อยู่ที่ "จังหวะที่ guard นั้นหลุด

คือเช็ค **invariant ของระบบ** (กลยุทธ์นี้ถือได้ไม้เดียว → pending กับไม้จริงห้ามอยู่พร้อมกัน) แล้วบังคับให้
เป็นจริงเสมอทันทีหลัง sync กับโลกจริง แทนที่จะไล่แก้ทีละจุดที่ state ปลอมอาจถูกใช้งาน
