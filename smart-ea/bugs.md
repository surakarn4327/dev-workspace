## 2026-09-19 — Dashboard ของ AdxEma ตัวหนังสือแถวหัวข้อทับกัน (colGap ตายตัวเกินไป)

**อาการ**: ผู้ใช้ส่งสกรีนช็อตจริงมา — แถวหัวข้อบน dashboard ("AdxEma XAUUSDc,M1") ทับกับข้อความ status
("Algo Trading อยู่") อ่านไม่ออกเป็น "AdxEmaXAUUSDcM1Algo Trading อยู่" ปนกัน

**สาเหตุจริง**: พอร์ต `AdxEmaDrawDashboard()` มาจาก `SatsDrawDashboard()` ตรงๆ รวมทั้งค่า `colGap = 170`
(ระยะจากขอบซ้ายกล่องถึงคอลัมน์ value) ที่เป็นตัวเลขคงที่ — ค่านี้พอดีสำหรับหัวข้อ "SATS XAUUSDc M1" (สั้น)
แต่ "AdxEma XAUUSDc,M1" ยาวกว่า 2 ตัวอักษร (ชื่อกลยุทธ์ "AdxEma" 6 ตัวยาวกว่า "SATS" 4 ตัว) ทำให้ข้อความ
หัวข้อ render กว้างเกิน 170px แล้วล้นทับคอลัมน์ status ที่ตรึงตำแหน่งไว้ตายตัว — เลขคงที่ที่ก็อปมาจากไฟล์
ต้นแบบไม่ได้ผูกกับความยาวข้อความจริงของ EA ตัวใหม่เลย

**วิธีแก้**: เพิ่ม `AdxEmaTextWidth()` วัดความกว้างข้อความจริงด้วย `TextSetFont()`/`TextGetSize()` (native
MQL5 GDI text measurement) แทนเลขคงที่ — คำนวณ `colGap`/`panelW` จากความกว้างจริงของข้อความหัวข้อ
(`"AdxEma " + _Symbol + " " + tf`) บวก margin กันเผื่อ 15% (เผื่อวัดคลาดเคลื่อนจาก DPI/font ต่างเครื่อง)
และมี fallback เป็นสูตรประมาณ (ตัวอักษร×ฟอนต์×0.65) ถ้า `TextGetSize()` คืนค่า 0 โดยไม่คาดคิด compile
ผ่าน 0 errors — **ยังไม่เคยเห็นผลจริงว่าแก้ครบ 100%** (แก้จากอ่านโค้ด+สกรีนช็อตที่ส่งมา ไม่ใช่จากการแนบ
EA ทดสอบเองโดยตรง) ผู้ใช้ควรแนบ EA ใหม่แล้วดูว่าหัวข้อไม่ทับกันแล้วจริงก่อนเชื่อว่าจบ

**บทเรียน**: **เลขตำแหน่ง/ระยะห่างที่ก็อปมาจาก EA ต้นแบบ (SATS) ผูกอยู่กับความยาวข้อความเฉพาะของ EA
ต้นแบบนั้น ไม่ใช่ค่าที่ปลอดภัยสากล** — ทุกครั้งที่พอร์ต UI/dashboard จาก EA อื่นที่ชื่อกลยุทธ์/label ยาว
ไม่เท่ากัน ต้องเช็คว่าเลขคงที่ (padding, colGap, panelW) ยังพอดีกับข้อความจริงของ EA ใหม่หรือเปล่า

**อัปเดต (รอบ 2 หลังผู้ใช้ส่งสกรีนช็อตกลับมา)**: ทางแก้แรกที่ใช้ `TextSetFont()`/`TextGetSize()`
(native API วัดข้อความจริง) **ผิดคนละทาง** — คาดว่า `size` เป็นบวก = "จุด × 10" ตรงกับหน่วยของ
`OBJPROP_FONTSIZE` แล้วส่ง `fontSize*10` เข้าไป ผลคือกล่อง dashboard กว้างพองจนกินเกือบเต็มความกว้าง
จอ (แทนที่จะแคบไป กลับกว้างเกินไปประมาณ 10 เท่า) — แปลว่าสมมติฐานเรื่อง scale/sign convention ของ
`TextSetFont` ผิด และ**ไม่มีทาง verify ได้จริงโดยไม่แนบ EA ทดสอบบนชาร์ตจริง** (compile ผ่านทั้งสองรอบ
เพราะเป็นแค่ค่าพารามิเตอร์ตัวเลข ไม่ใช่ syntax error) เปลี่ยนมาใช้สูตรประมาณจากจำนวนตัวอักษรแทน โดย
**คาลิเบรตค่าคงที่จากสกรีนช็อตจริง 2 รอบที่ผู้ใช้ส่งมา** (รอบแรกล้นที่ colGap=170 กับข้อความ 17 ตัวอักษร
ที่ FS=12 → ประมาณ 10px/ตัวอักษร) และ**เพิ่มเพดานบน-ล่างตายตัว** (`colGap` จำกัดช่วง 170-260) กันพลาด
ซ้ำแบบเดิมไม่ว่าค่าคงที่จะคลาดเคลื่อนแค่ไหนในอนาคต — บทเรียนเพิ่ม: **API ที่ไม่เคยใช้มาก่อนในโปรเจกต์
(ไม่มีตัวอย่างอ้างอิงในโค้ดเดิม) และมี sign/scale convention ที่จำจากความรู้เดิมไม่ได้แน่ชัด ไม่ควรเดาแล้ว
ส่งใช้เลย — ถ้าจะพึ่งความรู้ที่ไม่มั่นใจ 100% ต้องมีเพดานความปลอดภัย (hard cap) กำกับไว้เสมอ หรือใช้
สูตรประมาณที่คาลิเบรตจากข้อมูลจริงแทนซึ่งเชื่อถือได้กว่าการเดาความหมายของ API ที่ไม่คุ้นเคย**

## 2026-09-19 — AdxEma ไม่มี heartbeat monitor + ไม่เคลียร์ chart object ตอน OnDeinit

**อาการ**: ยังไม่เจอในบัญชีจริง — ผู้ใช้ขอให้เช็ค "ทำงานได้เหมือน best sats ทุกอย่างแน่นะ" รอบสุดท้าย
เลยไล่เทียบทุกฟังก์ชันของ `SelfAwareTrendCore.mqh` (SATS) กับ `AdxEmaCore.mqh` ทีละตัวแทนที่จะเช็คแค่
จุดที่เคยพังมาก่อน (ตามกฎห้ามเดา) พบ 2 ฟีเจอร์ที่ SATS มีแต่ AdxEma ไม่มีเลยตั้งแต่พอร์ตครั้งแรก:

1. **ไม่มี `OnTimer()` heartbeat** — SATS เช็คทุก 30 วิ (ไม่พึ่ง `OnTick` เลย เพราะถ้า tick หายไปจริง
   `OnTick` จะไม่ถูกเรียกด้วย ใช้ `OnTick` เช็คตัวเองไม่ได้) ว่า `TERMINAL_CONNECTED` หลุดไหม และไม่มี
   tick เข้ามาเกิน 120 วิไหม (EA แขวน/data feed ค้าง) แจ้ง Telegram แบบ dedupe ตามสาเหตุผ่าน
   `TG_NotifyProblemOnce`/`TG_ClearProblemKind` — `AdxEmaCore.mqh` ไม่เคยเรียก `EventSetTimer()` เลย
   จึงตรวจจับ "EA แขวน" แบบนี้ไม่ได้เลย
2. **`OnDeinit()` ไม่เคลียร์ chart object** — SATS ลบ object ทั้งกลุ่มลูกศร/เส้น SL-TP
   (`InpShowChartObjects`) และกลุ่ม dashboard (`InpShowDashboard`) ทิ้งตอน EA ถูกถอด/reattach —
   `AdxEmaCore.mqh` เดิมมีแค่ `PrintFormat` diagnostic ไม่เคยเรียก `PL_ClearChartObjects`/`ChartRedraw`
   เลย ทำให้ลูกศร/เส้น/พาเนล dashboard ค้างอยู่บนชาร์ตถ้าถอด EA ออก (จนกว่าจะเปลี่ยน template/รีเฟรช
   ชาร์ตเอง) — ไม่กระทบตรรกะเทรดแต่ผิดจากพฤติกรรมของ SATS

**วิธีแก้**: เพิ่ม `gLastTickMs`/`ADXEMA_HEARTBEAT_MAX_SEC` + `EventSetTimer(30)` ใน `OnInit()` +
`OnTimer()` พอร์ตตรงจาก SATS (เช็ควันหยุดสุดสัปดาห์ข้าม, เช็ค connection, เช็ค idle time) + อัปเดต
`gLastTickMs` ทุก `OnTick()` — และเพิ่ม `EventKillTimer()` + ลบ chart object ทั้งสองกลุ่มใน `OnDeinit()`
พร้อม `ChartRedraw()` เหมือน SATS ทุกประการ — **เพิ่มอีกจุดระหว่างเดียวกัน**: `OnInit()` เดิมเรียก
`WarmupEma()` ทันทีหลังสร้าง handle `iADX`/`iATR` โดยไม่รอให้ indicator คำนวณ buffer ครบก่อน (พบบ่อย
ตอน attach สดบนชาร์ตจริง handle ใหม่อาจมี lag) ต่างจาก SATS ที่มี wait loop รอ `BarsCalculated()` ก่อน
เสมอ (ข้ามใน Tester เพราะข้อมูลย้อนหลังพร้อมอยู่แล้ว) — เพิ่ม wait loop เดียวกันให้ AdxEma ด้วย compile
ผ่านทั้งหมด 0 errors 0 warnings

**บทเรียน**: **"เช็คจุดที่เคยพังมาก่อน" ไม่พอสำหรับคำถาม "เหมือนกันทุกอย่างไหม"** ต้องไล่ list ฟังก์ชัน
ทั้งหมดของไฟล์ต้นแบบ (`grep` หา signature ฟังก์ชันทุกตัว) แล้วเทียบทีละตัวว่ามี/ไม่มี/ไม่จำเป็นเพราะอะไร
ถึงจะมั่นใจได้จริงว่าไม่พลาดฟีเจอร์ cross-cutting (heartbeat, cleanup, ฯลฯ) ที่ไม่ได้ผูกกับตรรกะกลยุทธ์
โดยตรงแต่เป็นส่วนหนึ่งของ "EA ที่ใช้งานได้ปกติ" — ฟีเจอร์พวกนี้มักไม่โผล่มาเป็นบั๊กจนกว่าจะเจอสถานการณ์
จริง (data feed หลุด, ถอด EA) ซึ่งอาจไม่มีโอกาสได้ทดสอบก่อนใช้เงินจริงเลย

## 2026-09-19 — AdxEma ปิดไม้จาก cutoff/momentum-exit ไม่เคยแจ้ง Telegram เลย

**อาการ**: ยังไม่เจอในบัญชีจริง — พบระหว่างผู้ใช้ถามว่า "การแจ้งเตือน Telegram ล่ะ" หลังเพิ่ม dashboard
เสร็จ แล้วไล่เทียบทีละจุดที่ต้องแจ้ง Telegram ตามกฎ EA ข้อ 9 กับโค้ดจริง (ตามกฎห้ามเดา)

**สาเหตุจริง**: `PL_CloseAll()` ใน `PositionLib.mqh` **ไม่ส่ง Telegram อัตโนมัติเมื่อปิดสำเร็จ** (ส่งแค่
ตอนปิดไม่สำเร็จผ่าน `TG_NotifyProblem`) — การแจ้ง TP/SL ทำผ่านคนละกลไก คือ `PL_ClassifyClosed()` ที่
`PL_Manage()` เรียกทุก tick ตรวจจาก `DEAL_REASON_TP`/`DEAL_REASON_SL` เท่านั้น ส่วนการปิดมือแบบ
cutoff/momentum-exit ที่เรียก `PL_CloseAll()` ตรงๆ จะได้ `DEAL_REASON_CLIENT` ซึ่งไม่ตรงเงื่อนไขไหนใน
`PL_ClassifyClosed()` เลย **จึงไม่มีการแจ้ง Telegram เกิดขึ้นเลยสำหรับสองเหตุการณ์นี้** (มีแค่ `Print()`
และอัปเดต dashboard ในเครื่องเท่านั้น) ตรวจแล้วพบว่า `SelfAwareTrendCore.mqh` (SATS) รู้ปัญหานี้อยู่แล้ว
และแก้ไว้ตั้งแต่แรกด้วยการเรียก `SatsRecordClosedPosition()` (คำนวณ net P&L จากประวัติดีลของไม้ที่เพิ่ง
ปิด) ตามด้วย `TG_NotifyClose()` เองที่จุด timeout/flip-exit/cutoff-close ทุกจุด — `AdxEmaCore.mqh` ที่
เขียนจากศูนย์ไม่ได้ทำตามแบบนี้ตอนพอร์ตครั้งแรก

**วิธีแก้**: เพิ่ม `AdxEmaClosedNet()` ใน `AdxEmaCore.mqh` (มิเรอร์ `SatsRecordClosedPosition()`) อ่าน
`HistorySelectByPosition(gMtPosId)` (ตัวแปรนี้ `PL_CloseAll()` ตั้งใจไม่ล้างทิ้งให้ผู้เรียกอ่านประวัติต่อได้)
รวมกำไร/ขาดทุนของดีลขาออกทั้งหมด แล้วเรียก `TG_NotifyClose()` ทันทีหลัง `PL_CloseAll()` ทั้งใน
`CheckMomentumExit()` และ cutoff-close ของ `OnTick()` compile ผ่าน 0 errors

**บทเรียน**: **`PL_CloseAll()` ไม่ใช่ "จุดเดียวที่พอสำหรับปิดไม้แล้วจบ"** — มันแค่สั่งปิดออร์เดอร์เฉยๆ
ไม่รู้จัก "บริบท" ว่าทำไมถึงปิด (TP/SL อัตโนมัติจาก broker ปิดผ่านคนละ path คือ `PL_Manage`) EA ตัวไหน
ก็ตามที่เรียก `PL_CloseAll()` ตรงๆ เอง (คัตไม้ตามกฎ/exit ตามสัญญาณ) **ต้องเรียก `TG_NotifyClose()` เอง
เพิ่มด้วยเสมอ ไม่ได้มาพร้อมกันอัตโนมัติ** — เวลาพอร์ต EA ใหม่ที่มีจุดปิดไม้ด้วยเหตุผลอื่นนอกจาก TP/SL
(cutoff, timeout, flip-exit, momentum-exit ฯลฯ) ต้องไล่เช็คทุกจุดที่เรียก `PL_CloseAll()` ว่ามี
`TG_NotifyClose()` คู่กันหรือยัง ไม่ใช่แค่เชื่อว่า PositionLib "จัดการให้หมดแล้ว"

## 2026-09-19 — AdxEma (และ SdPaAdx) ไม่ sync ไม้จริงตอน OnInit — ช่องโหว่เดียวกับ SATS 2026-09-16

**อาการ**: ยังไม่เจอในบัญชีจริง — พบระหว่างตอบคำถามผู้ใช้ว่า "EA พร้อมรึยัง ตรวจบั๊กโดยใช้บทเรียนจาก

ก่อนตอบ (ตามกฎห้ามเดา)

**สาเหตุจริง**: `AdxEmaCore.mqh` (และ `SdPaAdxCore.mqh` เดิมด้วย) เก็บสถานะไม้ไว้ในตัวแปร global ของ

`PL_SyncOpenPosition()` เลย (ฟังก์ชันนี้มีอยู่แล้วใน `PositionLib.mqh` ตั้งแต่แก้บั๊ก SATS 2026-09-16 แต่
ไม่มี EA ตัวไหนอื่นเรียกใช้) — ถ้า reattach/compile ใหม่/เปลี่ยน timeframe ระหว่างมีไม้เปิดอยู่จริง `gMtDir`
จะรีเซ็ตเป็น 0 ทั้งที่ไม้ยังเปิดอยู่จริงในตลาด ผลคือ: (1) `PL_Manage()` เช็ค `gMtDir==0` แล้วข้ามการจัดการ
ไม้ทั้งหมด → **โหมด Fix Multiple RR หยุดแบ่งปิด TP1/TP2** (2) พอไม้นั้นปิดจริง โค้ดเช็ค `gMtDir != 0` ก่อน
เรียก `PL_ClassifyClosed()` — เพราะเป็น 0 ไปแล้ว **จะไม่มีการแจ้ง Telegram ตอนไม้นั้นปิดเลย** ผิดกฎ EA
ข้อ 9 (ส่วนการเข้าไม้ซ้ำไม่เกิดขึ้น เพราะ `CheckEntrySignal()` เช็ค `PL_HasPosition()` ซึ่ง query จาก
broker ตรงๆ ไม่ได้อิง `gMtDir`)

**วิธีแก้**: เพิ่ม `PL_SyncOpenPosition(InpMagic, 0);` ใน `OnInit()` ของ `AdxEmaCore.mqh` ทันทีหลัง
`WarmupEma()` compile ผ่าน 0 errors — **ยังไม่ได้แก้ `SdPaAdxCore.mqh`** เพราะ EA ตัวนั้นปิดเคสแล้ว
(ไม่พบ edge จริง ดูหัวข้อ SD_PA_ADX ด้านล่าง) ถ้าจะกลับไปใช้ต่อต้องแก้จุดนี้ด้วย

**บทเรียน**: **แก้บั๊กที่ root cause เป็น pattern ทั่วไป (เช่น "MQL5 global variable รีเซ็ตทุกครั้งที่ reload
แต่ไม้จริงไม่ได้ผูกกับ global") ต้องเช็คว่า EA ตัวอื่นที่ใช้สถาปัตยกรรมเดียวกัน (ใช้ `PositionLib.mqh`
เก็บสถานะไม้ใน global ตัวเดียวกัน) มีช่องโหว่เดียวกันไหมด้วยเสมอ ไม่ใช่แค่แก้ไฟล์ที่เจอปัญหาตัวเดียว** —
MQL5 ไม่มี inheritance ข้าม EA การแก้ใน `PositionLib.mqh` ครั้งเดียว (เพิ่มฟังก์ชันไว้) ไม่ได้แปลว่า EA
ทุกตัวเรียกใช้อัตโนมัติ ต้องไล่เช็ค `OnInit()` ของทุกไฟล์ที่ใช้ระบบเดียวกันทีละตัว
